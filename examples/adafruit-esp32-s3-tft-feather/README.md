# Adafruit ESP32-S3 TFT Feather (#5483)

This narrow profile boots a raw ESP32-S3 firmware image, powers and resets the
onboard ST7789, initializes it over GP-SPI2, paints an 8×8 red patch, and sends
a UART0 marker. It uses the existing ESP32-S3 chip model and adds board wiring;
it does not introduce a new silicon model.

The profile maps SPI2 SCK/MOSI to GPIO36/GPIO35, TFT_CS to GPIO7, TFT D/C to
GPIO39, TFT reset to GPIO40, the TFT/STEMMA QT rail enable to GPIO21, and the
backlight to GPIO45. The display descriptor models the controller's 240×320
frame memory and the fixed 135×240 RAM crop selected by Adafruit's rotation-1
offsets. The artifact keeps that crop in controller RAM orientation.

The board is ranked against demand rank **#1**, ESP32 family (38% reported
usage in the standing evidence). This is additional S3 board coverage, not a
new chip. The vendor availability snapshot is in
[`evidence/vendor-status.md`](evidence/vendor-status.md).

## Scope

- Exercised: ESP32-S3 GPIO, GP-SPI2, ST7789 SPI command/data framing, panel
  power/reset/backlight controls, frame-memory writes, and UART0 TX.
- Not claimed: flash/PSRAM behavior, Wi-Fi/BLE, the USB interfaces, buttons,
  STEMMA QT/I²C accessories, analog panel effects, or physical-board capture.
- The chip descriptor keeps its explicit SYSTEM placeholder; the smoke does
  not test dynamic peripheral clock or reset gating.
- SPI2's local W-buffer path is used; the smoke does not exercise SPI DMA.

Run the local smoke from the repository root:

```sh
RUSTC_WRAPPER= scripts/onboarding_smoke.sh \
  --target-id adafruit-esp32-s3-tft-feather \
  --script examples/adafruit-esp32-s3-tft-feather/onboarding-smoke.yaml \
  --system configs/systems/adafruit-esp32-s3-tft-feather.yaml \
  --firmware-build-script examples/adafruit-esp32-s3-tft-feather/ci/build-firmware.sh \
  --out-dir examples/adafruit-esp32-s3-tft-feather/evidence
```

The firmware source is [`firmware/tft_smoke.c`](firmware/tft_smoke.c). The
committed `evidence/` logs and `simulation-output/result.json` are generated by
the command above. The separate model-verification result records the hosted
oracle run when available.
