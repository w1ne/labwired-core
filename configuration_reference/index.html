    Configuration Reference

    LabWired uses a YAML-based configuration system to define the simulated hardware environment. This separation allows the same firmware binary to be tested against different hardware configurations (e.g., changing memory sizes or remapping peripherals) without recompilation.

    1. File Hierarchy

    A complete simulation requires two descriptor files:

    1. Chip Descriptor (chips/<name>.yaml): Defines the internal architecture of the SoC (Flash/RAM size, internal peripheral addresses).
    2. System Manifest (systems/<name>.yaml): Instantiates a chip and defines board-level wiring (external sensors, UART loopbacks).

    A chip descriptor loaded from a path may include: other chip YAMLs (§2), and a manifest's external_devices: entries resolve either to a model built into the engine or to a declarative device descriptor — configs/devices/*.yaml — whose behavior: primitives are the third, data-only configuration surface (§3, External devices).

    2. Chip Descriptor Schema

    Defines the invariant properties of the silicon.

    name: "STM32F103"
arch: "arm"
core: "cortex-m3"   # Exact CPU core; gates core-specific behavior
                    # (e.g. bit-band aliasing exists only on M3/M4)
flash:
  base: 0x08000000
  size: "64KB"  # Supports KB/MB suffixes
ram:
  base: 0x20000000
  size: "20KB"

peripherals:
  # Internal Peripheral Definition
  - id: "usart1"
    type: "uart"
    base_address: 0x40013800
    irq: 37
    config:
      profile: "stm32f1"  # Loads architecture-specific register map

  - id: "gpioa"
    type: "gpio"
    base_address: 0x40010800
    config:
      profile: "stm32f1"

  # Declarative Peripheral (Custom)
  - id: "my_custom_timer"
    type: "declarative"
    base_address: 0x40004000
    config:
      path: "../peripherals/custom_timer.yaml"

    Every chip key

    This is the complete ChipDescriptor surface (crates/config/src/chip.rs); the sample above is its common shape. name, arch, flash, ram, and peripherals are required (peripherals: [] is a valid chip with no MMIO); everything else is optional and has a default.

    Key Meaning Minimal example
    schema_version Free-form descriptor version; defaults to "1.0". schema_version: "1.0"
    name Part label; also how a manifest's bare-word chip: finds a built-in. name: "STM32F103"
    arch Instruction-set family: arm, riscv, xtensa, avr, unknown (family aliases like cortex-m3 are accepted). arch: "arm"
    core Exact core (cortex-m3, cortex-m33, cortex-m0+); gates per-core bus behavior — bit-band aliasing exists only on M3/M4. core: "cortex-m3"
    cpu_hz The clock the simulator runs the core at, in Hz. Declared, not derived — see Clock, schema and includes. 0 = undeclared. cpu_hz: 72_000_000
    flash Primary flash window: base, size, optional cpu_writes policy (see below). flash: {base: 0x08000000, size: "64KB"}
    ram Primary RAM window: base, size, optional cpu_writes. ram: {base: 0x20000000, size: "20KB"}
    reset_vector_offset Bytes from the flash base to the application vector table when a stage-2 bootloader precedes it (0 = vectors at the flash base). reset_vector_offset: 0x100
    flash_boot_alias true (default): address 0x0 mirrors flash (the STM32 boot alias). false for a part whose low addresses are real memory (i.MX RT ITCM at 0x0). flash_boot_alias: false
    atomic_register_aliases Register-alias flavour: false (default), true (= rp2040), rp2040, efr32s2. atomic_register_aliases: "efr32s2"
    ns_alias_offset TrustZone non-secure alias offset; applied only to otherwise-unmapped addresses, so it cannot shadow a declared peripheral. ns_alias_offset: 0x10000000
    memory_regions Extra CPU-visible windows beyond flash/ram — see Memory-map keys. see below
    peripherals MMIO peripheral list; see Peripheral entries. peripherals: []
    pins Authoritative pad→GPIO map; once declared, an unlisted pad no longer resolves (no silent label-letter fallback). pins: {PA5: {gpio: gpio_a, bit: 5}}
    analog_pins Pad→ADC map (peripheral, channel); kept apart from pins so naming only the ADC inputs does not force a full GPIO transcription. analog_pins: {PA0: {peripheral: "adc1", channel: 0}}
    io_voltage_v The supply the chip's GPIO pads run from, in volts; reference for gpio_input_thresholds. Absent = "not transcribed" (nothing defaults it). io_voltage_v: 3.3
    gpio_input_thresholds Digital input thresholds as ratios of io_voltage_v; must satisfy 0 < vil < vih < 1. gpio_input_thresholds: {vil: 0.35, vih: 0.65}
    supply_monitor POR/PDR/BOR supply thresholds — see Supply supervisor. see below
    include Chip YAML include(s), expanded only when the descriptor is loaded from a path. include: nrf52-common.yaml

    cpu_writes — the memory-region store policy

    flash: and ram: are memory regions: base, size, and the optional cpu_writes policy. The policy says what the bus does with a CPU-initiated store into that region; it is independent per region and defaults to allow (the only behaviour that existed before the key):

    # configs/chips/ci-fixture-stm32l476-readonly.yaml
flash:
  base: 0x08000000
  size: "1024KB"
  cpu_writes: fault   # allow (default) | warn | fault
ram:
  base: 0x20000000
  size: "96KB"        # omitted cpu_writes ⇒ allow
    Mode A CPU store into the region… Recorded when the store is flagged or refused
    allow (default) commits silently, exactly as before this region records nothing
    warn commits; one deduplicated WARN per region violation count + first {addr, cycle, pc}
    fault does not commit; raises SimulationError::MemoryViolation(addr) violation count + first {addr, cycle, pc}

    The semantics, precisely (crates/config/src/chip.rs CpuWritePolicy, crates/core/src/bus/memory_policy.rs, crates/core/src/bus/accessors.rs):

    • CPU stores only. The gate sits at the top of the CPU store path for every access width (write_u8/16/32/64) before anything commits. Host/loader writes never pass through it: loading an image whose segments land inside flash:/ram: writes the backing memory directly (Machine::load_firmware → LinearMemory::load_from_segment), and a snapshot restore is the same. The generic DMA request path runs with the gate explicitly bypassed; peripheral-internal DMA models that write through &mut dyn Bus are a recorded deferral, not part of this rule yet.
    • The boot alias counts as flash. A store through the boot alias (address 0x0 on a flash-at-0x08000000 part) is gated as a flash store.
    • fault → precise BusFault. The store raises SimulationError::MemoryViolation(addr). On an ARMv7-M core with BusFault enabled that is a precise data BusFault with BFAR valid, and the CLI's verdict names the region when the fault address matches the first recorded violation in a fault-mode region (crates/cli/src/fault_report.rs): data access at 0x0800_1000 (BFAR valid; store to read-only flash).
    • warn commits and records. The store lands exactly as with allow; one WARN is logged for the first violation in the region and no more — the count and the first violation are still recorded in full.
    • result.json.memory_policy is skip-on-default. labwired test writes the block only when at least one of the two regions is non-allow; an all-default config produces byte-identical artifacts to before the key existed. Each region carries mode, violations, and first (addr, cycle, pc; omitted when there were none).

    Runnable receipt: examples/readonly-flash/ runs a firmware store into cpu_writes: fault flash end to end, and Add a board shows the flip to warn.

    Known caveat — images linked at the boot alias. A segment whose address is not inside the flash/RAM backing (an ELF linked at 0x0 on a part whose flash sits at 0x0800_0000) is loaded byte-by-byte through the bus (Machine::load_firmware falls back to one bus store per byte), and those load stores are subject to cpu_writes like any other. With cpu_writes: fault on flash, such an image cannot load: the first store is refused and the segment fails — the Cortex-M loader logs Failed to load segment at 0x0 - outside of memory map and continues with a blank flash. Link firmware at the flash base, as real parts' images are; the read-only-flash example is linked at 0x0800_0000, so its own load is direct and recorded as zero violations.

    Memory-map keys beyond flash/ram

    • reset_vector_offset — where the real reset vector hides when a stage-2 bootloader precedes the application. The simulator does not execute the stage-2 blob (flash is directly mapped); it uses this offset to find the vector table when the flash-base vectors are not valid. RP2040 sets 0x100 (the boot2 blob). 
      reset_vector_offset: 0x100            # configs/chips/rp2040.yaml
    • flash_boot_alias (default true) — whether address 0x0 mirrors the flash image. Set false for a part whose low addresses are memory of their own; on the i.MX RT the ITCM sits at 0x0, and with the alias on a store there would be written into flash. 
      flash_boot_alias: false               # no in-tree chip needs it today
    • atomic_register_aliases — the 0x1000-strided aliases of every peripheral register that a family's HAL uses for read-modify-write. Two families use the SAME stride with DIFFERENT ops, so the value names the flavour:
    • rp2040: +0x1000 XOR, +0x2000 SET, +0x3000 CLR (also RP2350);
    • efr32s2: +0x1000 SET, +0x2000 CLR, +0x3000 TGL (EFR32/EFM32 Series 2).

    The historical boolean spelling still loads: true == rp2040; false (or omitting the key) means an alias address is ordinary unmapped MMIO. 

    atomic_register_aliases: true         # configs/chips/rp2040.yaml
atomic_register_aliases: "efr32s2"    # configs/chips/efr32mg26.yaml
    - ns_alias_offset — the TrustZone non-secure alias window. An MMIO access that maps to no peripheral but whose address plus this offset DOES map to one is served by that peripheral; the offset applies only as a fallback, so it can never shadow a declared peripheral. The nRF54L family exposes every peripheral at 0x5000_0000+ (secure) and exactly 0x1000_0000 below it. 
    ns_alias_offset: 0x10000000           # configs/chips/nrf54l15.yaml
    - memory_regions — additional CPU-visible windows beyond flash/ram (ESP32-C3 IRAM 0x4037C000 and flash-DROM view 0x3C000000, the RP2040 bootrom). Each entry has name, base, size, and optionally: - image_env — an environment variable naming a raw binary loaded into the region at base (a mask-ROM dump, say). The region stays zero-filled when the variable is unset or the file is missing. - erased — fill the region with 0xFF instead of 0x00. An erased flash byte reads ones, so a blank settings page must read ffffffff … in the twin too.

    # configs/chips/efr32mg26.yaml (excerpt)
memory_regions:
  - name: "userdata"
    base: 0x0FE00000
    size: "1KB"
    erased: true

    Peripheral entries

    Each peripherals: entry is a PeripheralConfig (crates/config/src/chip.rs):

    Key Meaning Minimal example
    id Instance name; clock:, board_io: and external_devices[].connection cite it. id: "usart1"
    type Model selector; an unrecognised type fails the load (see below). type: "uart"
    base_address MMIO window base; accepts 0x… or an underscored integer. base_address: 0x40013800
    size Optional window length. size: "1KB"
    irq Vector line: irq: 37, or irq: nvic@37 to name the controller in one token. irq: 37
    irq_controller Controller id when not given by the controller@line sugar. irq_controller: "nvic"
    clock RCC gate(s) that must ALL be set for the block to answer: one {reg, bit} or a list. reg is a symbolic enable-register name resolved at build time; a name the family does not expose is a hard build error. Absent ⇒ never gated. clock: {reg: "apb2enr", bit: 14}
    config Instance knobs. Unknown top-level keys flatten in here (easyDMA: true ≡ config: {easyDMA: true}); nested config: wins on a colliding key. config: {profile: "stm32f1"}

    The clock: mechanism (one gate or several ANDed) is documented in the Peripheral modeling guide; declarative register blocks in Declarative Register Definitions.

    Supported Peripheral Types

    • uart, usart: Universal Asynchronous Receiver Transmitter
    • gpio: General Purpose I/O
    • rcc: Reset and Clock Control
    • timer: Basic Timer
    • i2c: Inter-Integrated Circuit
    • spi: Serial Peripheral Interface
    • exti: External Interrupt Controller
    • afio: Alternate Function I/O
    • dma: Direct Memory Access Controller
    • systick: System Tick Timer
    • declarative: Loads a generic peripheral from a YAML register description.
    • strict_ir: Loads a register map from Strict IR JSON.
    • stub: A zero-filled window — only for types on the explicit known-stub allowlist (crates/core/src/bus/known_stubs.rs, shrink-only, each entry with a written reason).

    Family factories add family-specific types (nrf52_uart, esp32c3_i2c, imxrt_lpi2c, …). An unrecognised type is a load error, never a silent zero-filled stub: the message tells you to model it, describe it with type: declarative plus a descriptor path, or — if answering zeros really is right — declare type: stub (or add the type to the allowlist with a reason).

    Pin maps and pad voltage

    Key Meaning Minimal example
    pins Authoritative pad label → {gpio, bit} map. When a chip declares any pins, resolution goes through the map, so a pad whose label implies the wrong port still resolves correctly — and an undeclared pin fails to resolve instead of silently letter-parsing onto a port. Extra fields (e.g. functions:) are ignored by the simulator. pins: {PA5: {gpio: gpio_a, bit: 5}} (configs/chips/atsamd21g18a.yaml)
    analog_pins Pad label → the ADC that samples it (peripheral, channel), transcribed from the datasheet pinout. A pad absent here means "no analog pad is modelled", not "channel 0": the co-simulation board.analog.<pad>_volts path refuses such a pad rather than guessing. analog_pins: {PA0: {peripheral: "adc1", channel: 0}} (configs/chips/stm32f103.yaml)
    io_voltage_v The supply the GPIO pads run from, in volts. Absent means "not transcribed", and nothing defaults it — a board at another supply would get thresholds for the wrong rail. io_voltage_v: 3.3
    gpio_input_thresholds Datasheet digital input thresholds as ratios of io_voltage_v: a pad reads low at or below vil and high at or above vih. gpio_input_thresholds: {vil: 0.35, vih: 0.65} (configs/chips/stm32f103.yaml)

    Supply supervisor

    supply_monitor: transcribes the part's reset and power-control thresholds: the MCU is held in reset until VDD rises to por_rising_v (and, with a brown-out level active, to that level's rising_v); it resets again when VDD falls below pdr_falling_v or the active level's falling_v. It is only consulted when a board routes its VDD net into the engine (board.power.vdd_volts); absent means the chip cannot be held in reset by its supply, and such a route is refused rather than guessed.

    # configs/chips/stm32f401.yaml (excerpt)
supply_monitor:
  por_rising_v: 1.72
  pdr_falling_v: 1.68
  bor_levels:
    bor1: { falling_v: 2.19, rising_v: 2.29 }
    bor2: { falling_v: 2.50, rising_v: 2.59 }
    bor3: { falling_v: 2.83, rising_v: 2.92 }
  # bor_level: bor1    # optional: the level in effect (absent = BOR disabled)

    Clock, schema and includes

    • cpu_hz — declared, not derived. Nothing walks RCC/PLL registers to compute a clock. This number is the single source of truth for every "how many cycles is a microsecond" question, and self-timed device models (DHT22, WS2812, the rotary encoder) scale their datasheet windows by it, so it must agree with the clock the firmware was built against or the firmware decodes noise. 0 means undeclared; every in-tree chip declares it (every_chip_descriptor_declares_a_cpu_hz fails the build if a new one does not). A board that runs the part slower overrides it with the manifest's cpu_hz: — the NUCLEO-L476RG never leaves the 4 MHz MSI reset clock and says so in its manifest. 
      cpu_hz: 80_000_000
    • schema_version — descriptor version string, defaults to "1.0". No engine behaviour keys off it; it is provenance. 
      schema_version: "1.0"
    • include — chip YAML include(s), expanded only when the descriptor is loaded from a path (ChipDescriptor::from_file); built-in chips cannot include because there is no filesystem. Paths are relative to the including file, includes load first, and local keys win. peripherals merge by id, memory_regions by name, pins/analog_pins as maps. 
      include: nrf52-common.yaml       # or: include: [a.yaml, b.yaml]

    3. System Manifest Schema

    Defines the board-level environment.

    name: "BluePill Board"
chip: "../chips/stm32f103.yaml"  # Path relative to this file

# Accepted but ignored today: the engine has no `connectors:` field (see the
# note under "Every manifest key"). Console routing is `debug_uart:`; external
# buses are `external_devices:`. Nine in-tree system manifests still carry this
# block, so it is documented rather than deleted.
connectors:
  - type: "uart"
    peripheral: "usart1"
    endpoint: "host_console"  # Pipes UART output to simulator stdout

    Every manifest key

    This is the complete SystemManifest surface (crates/config/src/manifest.rs). name and chip are required; everything else is optional.

    Key Meaning Minimal example
    schema_version Defaults to "1.0"; environment manifests must declare "1.0" exactly. schema_version: "1.0"
    name Board label; used in logs and to name a private lab air. name: "BluePill Board"
    chip A bare word (stm32f103) is a built-in/plugin chip name; anything containing /, \, or ending .yaml/.yml/.json is a path resolved relative to THIS manifest, so a manifest is relocatable with the files it names. chip: "stm32f103"
    cpu_hz Board-level override of the chip's declared clock, in Hz. Absent ⇒ the chip's default. cpu_hz: 4_000_000 (configs/systems/nucleo-l476rg.yaml)
    memory_overrides Parsed but not consulted by the engine today — region sizes come from the chip descriptor. The field exists so manifests may carry it; do not rely on it. memory_overrides: {flash: "512KB"}
    peripherals Chip-peripheral patches/additions. An entry whose id matches a chip peripheral merges its config keys and overrides base_address (when nonzero; 0 keeps the chip's), irq and size; an unmatched id adds a new peripheral. id, type and base_address are required on every entry. peripherals: [{id: "usart1", type: "uart", base_address: 0, config: {profile: "stm32f1"}}]
    external_devices The parts on the board's buses — see External devices. see below
    parts Manifest-carried part packs (private/vendor catalogs). The labwired.part/v1 contract lives in Part packs; - path: is a CLI convenience that SystemManifest::from_file inlines, so a manifest handed straight to the browser/engine must carry the pack inline. parts: [{path: "./acme.yaml"}]
    cosim_models Scalar signal-level co-simulation plants — see Co-simulation and motor models. see below
    motor_models Typed motor plants (kind: dc or kind: bldc) with SI-unit fields. see below
    board_io Board-level pin bindings — see Board I/O. see below
    debug_uart Which console the board's USB socket is wired to; see its section below. debug_uart: "uart0"
    wifi_ap Opt-in per-lab virtual WiFi AP — see WiFi AP. Absent ⇒ no AP. see below
    walk_deleted Per-cycle peripheral-walk deletion: absent = auto-derive, true = force deleted, false = pin on. Only consulted in event-scheduler builds; a legacy build always walks. walk_deleted: true (examples/nokia5110-invaders-lab/system.yaml)

    connectors: — nine in-tree system manifests (arduino-uno-r4-minima, calliope-mini-v1, metro-m4, microbit-v1, microbit-v2, nano-33-iot, pybadge, stm32f7-discovery, teensy-41) still carry a connectors: block that the engine ignores; their consoles work through the defaults meanwhile. One day core may parse it; today it is not a configuration surface.

    walk_deleted in full (crates/config/src/manifest.rs): absent means the core auto-derives walk-deletability at build time — the walk is deleted iff EVERY peripheral on the bus is provably walk-independent for all firmware states (conservative). true is a hand opt-in for a config verified byte-identical walk-free; false pins the walk on.

    External devices

    Each external_devices: entry:

    Key Meaning
    id Instance name. board_io and stimulus channels address the device by it, and mux children name it as their connection.
    type The device model — see the catalog below. An unknown type is a hard load error; nothing is silently skipped.
    connection What the device hangs off: normally a controller peripheral id ("i2c1", "spi1", "uart2"), or a GPIO peripheral id for pin-timing parts. It may also name ANOTHER external device's id — that is how a slave is placed behind a TCA9548A bus switch.
    channel Downstream channel on a bus switch (0..=7; absent behind a switch means 0). Meaningless and ignored when connection names a controller.
    route Optional signal→pad route: sda/scl, mosi/miso/sck, tx/rx. Required by controllers whose pads are runtime-routed — an ESP32-C3 I²C rejects a missing route because its GPIO matrix makes the wiring runtime-configurable.
    config Per-device knobs (i2c_address, pin labels, seeds, …); the model's metadata lists the keys it reads.

    Resolution order — one implementation in crates/core/src/bus/external_devices.rs:

    1. the manifest's own parts: packs (most specific wins);
    2. the built-in kit registry (the catalog below);
    3. the declarative configs/devices/*.yaml descriptors.

    Anything still unclaimed fails the build with the manifest id and type named.

    The catalog is generated from the kit registry into crates/core/tests/fixtures/peripherals/manifest.json (regenerate with cargo run -p labwired-cli --bin gen-peripherals-manifest).     Device descriptors (external parts as data)

    Every model in the catalog is a device descriptor: the in-tree ones live in configs/devices/*.yaml, and a manifest can carry its own in parts:. The top-level keys (crates/config/src/peripherals.rs DeviceDescriptor):

    Key Meaning
    type The type: string the manifest uses — a descriptor's identity.
    behavior Which runtime primitive backs the part and how its pins/registers are declared.
    emit How the canvas compiler emits this device into a manifest (used by the browser compiler; optional).
    metadata Display labels, accepted config: keys, and the stimulus channels the part serves — load-bearing: the same channel definitions back the device's SimInput impl.
    schema Contract version — required of a manifest-carried pack (labwired.part/v1).
    source Provenance (which catalog/vendor shipped the pack), so errors can name where a model came from.
    overrides The built-in type this pack deliberately replaces; shadowing a built-in is otherwise a hard error.
    catalog App-layer catalog record (opaque to the simulator).

    behavior.primitive selects the interpreter (one line each):

    Primitive What the engine interprets
    i2c_device Register-pointer I²C part (the i2c: block).
    spi_device SPI register/frame part (the spi: block).
    display Framebuffer panel: geometry, pixel format, RAM layout, command/data framing.
    led_strip Addressable LED strip: wire protocol plus the artifact it publishes.
    analog_source ADC-channel plant: the datasheet's output curve.
    uart_device Byte-stream part: frame shape, command table, unsolicited output.
    uart_transceiver A part that gates a UART (driver/receiver enable pads).
    gpio_device Pin-timing part driven by rules and finite edge schedules.
    logic_gate 74-series truth table, enables, direction/select, propagation delay.
    segment_display Multiplexed 7/14/16-segment display.
    led_matrix Row/column multiplexed LED matrix.
    analog_mux Analog multiplexer: select pins, channel count, enable.
    dc_motor / bldc_motor Motor plants — converted to the typed plants at the loader boundary.

    The wire-level detail (register encoding keys, schedules, artifacts, rules) lives in Part packs; declarative register blocks for chip peripherals live in Declarative Register Definitions. Worked examples: configs/devices/adxl345.yaml (I²C), configs/devices/dht22.yaml (one-wire GPIO), and the howtos under Extend LabWired.

    Co-simulation and motor models

    cosim_models: declares scalar signal-level plants stepped in lockstep with the machine: id, adapter (external_process, fmi, mock, analog), model (required for external_process and fmi), step_ns (default 1000), inputs/outputs (signal name → board.* route) and free-form config. The analog adapter needs config.netlist (a path) or config.netlist_text (inline) plus config.probes. Deep reference: External-process co-simulation.

    # examples/cosim-spice-rc/system.yaml (excerpt)
cosim_models:
  - id: "rc_lowpass"
    adapter: "external_process"
    model: "./models/rc_lowpass.py"
    step_ns: 100000            # 100 us; RC tau is 1 ms
    inputs:
      gpio: "board.gpio.pa5"
    outputs:
      v_out: "board.analog.pa0_volts"
    config:
      protocol: "jsonl"
      engine: "ngspice"
      netlist: "./rc.cir"

    motor_models: declares typed deterministic motor plants — kind: dc (brushed) or kind: bldc — with SI-unit fields (resistance, inductance, torque/back-EMF constants, inertia, friction, supply, encoder CPR) and pad bindings; see examples/nucleo-l476rg-bldc/system.yaml for the full BLDC form. A motor can equivalently be declared as an external_devices entry with type: dc-motor or bldc-motor: the loader converts it to the same typed plant (MotorModelConfig::from_external_device), so the two spellings cannot drift.

    # examples/f401-hbridge-dc-motor/system.yaml (excerpt)
external_devices:
  - id: motor
    type: dc-motor
    connection: gpio
    config:
      resistance_ohm: 1.2
      inductance_h: 0.002
      torque_constant_nm_per_a: 0.08
      back_emf_constant_v_per_rad_s: 0.08
      rotor_inertia_kg_m2: 0.00004
      viscous_friction_nm_per_rad_s: 0.00001
      coulomb_friction_nm: 0.006
      supply_voltage_v: 12.0
      load_torque_nm: 0.0
      encoder_cpr: 1024
      simulation_clock_hz: 84000000
      in1_pin: PA0
      in2_pin: PA1
      both_inputs_low: brake
      pwm_pin: PA6
      timer_name: tim3
      timer_channel: 1

    A kind: dc motor can instead put its winding in an analog netlist with armature: circuit. The netlist carries the winding as series R + L + a back-EMF voltage source under whatever switch, flyback diode and rail drive it (a low-side transistor, a bridge, a relay — any MCU); it routes the solved winding current in on board.motor.<id>.current_a and reads the motor's back-EMF on board.motor.<id>.back_emf_v (see cosimulation_plugins.md). The plant then only turns that current into torque and integrates the shaft, so the supply is the netlist's wired rail: supply_voltage_v, pwm_pin and the direction / brake / enable / timer keys are refused. Every motor also publishes motor.<id>.speed_rpm and motor.<id>.current_a change-point series in analog_series (with armature: circuit, current is absent until routed). The netlist may also route the rail feeding the winding in on board.motor.<id>.supply_v; the motor reports it as its bus_voltage_v (0 while unrouted).

    Both motor kinds take an optional coulomb_friction_nm (default 0): dry bearing and brush friction, a constant torque opposing rotation that also holds a resting shaft until the drive exceeds it. Viscous drag alone never stops a shaft — the catalog motor's 10 µN·m·s/rad over a 40 g·cm² rotor is a 4 s time constant — so the catalog dc-motor part defaults it to 6 mN·m, which stops a coasting fan in well under a second.

    motor_models:
  - kind: dc
    id: fan
    armature: circuit          # default: bridge
    resistance_ohm: 1.2
    inductance_h: 0.002
    torque_constant_nm_per_a: 0.08
    back_emf_constant_v_per_rad_s: 0.08
    rotor_inertia_kg_m2: 0.00004
    viscous_friction_nm_per_rad_s: 0.00001
    coulomb_friction_nm: 0.006
    load_torque_nm: 0.0
    encoder_cpr: 12
    simulation_clock_hz: 16000000

    Board I/O

    board_io: is the board-level pin vocabulary: an LED soldered to a pad, a button a user can press, an ADC input. Entries are BoardIoBinding:

    Key Meaning
    id Binding name; also the stimulus channel for a drivable contact.
    kind led, button, adc_input, pwm_output, i2c_device, spi_device, uart_device.
    peripheral The peripheral id (from the chip or a manifest patch) that owns the pin.
    pin Bit within that peripheral's port / ADC channel number.
    signal output (default) or input. A kind: button binding with signal: input is additionally materialised as a drivable button stimulus; an output-kind button is not a contact the firmware samples.
    active_high Polarity, default true.
    i2c_address For kind: i2c_device bindings.
    device_type The external-device type this binding surfaces, for the browser.
    channel Stimulus channel this contact exposes when it is not a plain pressed button (obstacle, field, vibration, …); absent means pressed.

board_io:
  - id: "led_ld2"
    kind: "led"
    peripheral: "gpioa"
    pin: 5
    signal: "output"
    active_high: true
  - id: "button_b1"
    kind: "button"
    peripheral: "gpioc"
    pin: 13
    signal: "input"
    active_high: false

    ST7789 physical glass window

    For st7789-170x320 external devices, the optional config keys col_offset, row_offset, cols, and rows describe the glass in physical 240×320 frame-memory coordinates. Supply all four together. For a module exposing columns 35–204 and all 320 rows, use col_offset: 35, row_offset: 0, cols: 170, and rows: 320; the offsets are module integration values.

    The configured framebuffer and artifact dimensions remain 170×320 regardless of MADCTL rotation or mirroring. MADCTL controls how firmware writes map into physical memory, while the glass stays fixed. Without a configured window, the framebuffer uses firmware coordinates and reports 240×320 or 320×240 according to MADCTL's row/column exchange bit.

    debug_uart — which console the board's USB socket is wired to

    debug_uart: "usb_serial_jtag"   # ESP32-C3 SuperMini, ESP32-S3 Zero
debug_uart: "uart0"             # CP210x/CH34x bridge boards
debug_uart: "uart1"             # a board that routes its console elsewhere

    An ESP32-C3 or -S3 has two consoles in silicon: UART0 and the chip's own USB-Serial-JTAG block. Which one carries Serial to the developer's cable is neither a chip fact nor a firmware fact — it is a BOARD fact, decided by what the USB socket is soldered to:

    board's USB socket console Serial build flag
    native USB USB-Serial-JTAG ARDUINO_USB_CDC_ON_BOOT=1
    USB-UART bridge IC UART0 ARDUINO_USB_CDC_ON_BOOT=0

    The build flags and this key must come from the SAME board fact. If they disagree, firmware built for one console runs against a twin listening on the other and the Serial pane stays empty — which is exactly what a real board does when the flags are wrong, and exactly what shipped: a hosted build flashed to a real ESP32-C3 SuperMini printed the ROM and bootloader banners and then nothing, because Serial was on UART0 and a SuperMini's USB-C is not.

    The engine taps ONE console, the declared one, because a real board gives you one cable. It records the other and reports what the firmware said there (WasmSimulator::console_mismatch) so a silent pane has a reason. A declared console the bus does not have is refused at construction rather than silently substituted — see crates/core/src/console.rs.

    Omit the key to keep each path's historical default (UART0 on the ESP32-C3 merged-flash paths; every console-capable UART elsewhere).

    For an inputs.env CI world, each nodes[].system value points to this same System Manifest format used by the Playground. The environment manifest adds node IDs, firmware paths, and explicit interconnects; it does not create a second board-configuration dialect. v0.19 world manifests reject nodes[].config_overrides: the field must be omitted, including {} and null. Each resolved node chip must resolve to arch: arm and declare core: cortex-m*; its firmware must be an EM_ARM ELF with a valid Cortex-M Thumb reset vector at flash.base + reset_vector_offset (SP in RAM and Thumb-bit reset handler in flash). See the CI Test Runner for the closed world-interconnect schema.

    A node may set profile: arduino-esp32, the same boot profile a test script names in inputs.profile: a classic-ESP32 (Xtensa LX6) node running an Arduino-ESP32 sketch ELF then takes the Arduino fast boot (install_arduino_esp32_profile). Any other value, or the profile on any other chip, is refused, and a world admits one such node (the profile's boot thunks keep per-thread state). ESP32-S3 and ESP32-C3 nodes need no profile; their mask ROMs are provisioned like the single-chip engine's (in the browser, passed as the node's blobs).

    World completion stays in the inputs.env test script, not the manifest. Set limits.stop_when_assertions_pass: true to opt into a durable early completion: all node-qualified assertions must pass at or after the optional stop_when_assertions_pass_min_steps floor and remain true for the optional stop_when_assertions_pass_settle_steps window (default 100000). The default is false; a same-round runtime failure or wall_time_ms, max_cycles, or max_uart_bytes limit takes precedence over assertions_passed. max_steps remains the outer execution bound, so an all-pass final world round reports assertions_passed.

    4. CLI Usage

    To run a simulation, provide both the firmware and the system manifest:

    labwired --firmware firmware.elf --system configs/systems/bluepill.yaml

    The simulator loads the system manifest, resolves the chip descriptor, initializes the memory map, and begins execution at the Reset Vector.
