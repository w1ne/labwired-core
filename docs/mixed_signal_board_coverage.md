# Mixed-signal board coverage

This inventory tracks every system profile in `configs/systems/*.yaml` (including demos,
fixtures, and multiple profiles for the same physical board). A profile is covered only when
a board-specific test solves an analog device/netlist, routes it to a modeled board endpoint,
and asserts the result. Endpoints include an ADC conversion or a voltage-thresholded digital
input on profiles without an ADC or without an externally routable ADC input. A GPIO-only proof
does not imply ADC support. Generic chip bus tests, analog output traces without a board endpoint,
and device-only unit tests do not count.

Current inventory: **103 top-level profiles; 103 have end-to-end analog coverage; 0 have no end-to-end analog coverage.** The 26 exact-part profiles in `configs/systems/stm32-catalog/` are also covered (see [STM32 catalog profiles](#stm32-catalog-profiles)). Of the 245 imported profiles in `configs/systems/onboarding/`, 193 are covered end to end through a GPIO input (17 of them also through every ADC instance they declare, 30 simavr AVR parts also through a firmware conversion on their CPU-owned ADC, and the 3 ATtiny2313/2313A/4313 and the AT90USB162 through their analog comparator), 3 more (`stm32h7`, `stm32h747`, `stm32h747-disco`) only through their ADCs, and 49 declare neither a GPIO input nor a convertible ADC (see [Onboarding profiles](#onboarding-profiles)). Each round selects the next uncovered profile and extends shared device, netlist, or routing support where needed. Coverage through GPIO thresholds does not imply ADC support.

## STM32 catalog profiles

All 26 exact-part smoke profiles in `configs/systems/stm32-catalog/*.yaml` (STM32F103 C/R/T x4/x6 including the `h` BGA variants, STM32F401 C/R/V xB–xE, STM32F407 V/Z/I xE/xG) are covered by one descriptor-driven proof: [`cosim_stm32_catalog_analog.rs`](../crates/core/tests/cosim_stm32_catalog_analog.rs)::`every_stm32_catalog_profile_routes_ntc_and_diode_netlists_into_adc1`. For each part it reads ADC1's base, register profile (F1 or F4) and clock gate from the chip descriptor, then routes the generic Beta NTC divider to PA0 and the unrelated Shockley diode to the package's highest-numbered bonded ADC1 pad (PB1/IN9 on 36- and 48-pin packages, PC5/IN15 on 64-pin and larger). Both solved voltages are checked against independent references and read back through a firmware-style one-shot conversion. On packages without PC0, a route to `board.analog.pc0_volts` must fail at binding time. The test enumerates the directory, so a new catalog profile is covered without editing the test, and the asserted profile count flags it for this inventory.

## Onboarding profiles

The 245 imported profiles in `configs/systems/onboarding/*.yaml` are inventoried by one descriptor-driven proof: [`cosim_onboarding_analog.rs`](../crates/core/tests/cosim_onboarding_analog.rs)::`every_onboarding_profile_with_a_convertible_adc_routes_ntc_and_diode_into_each_instance`. For each profile it reads every non-stub ADC from the chip descriptor, picks the converter family from the peripheral type and `config.profile`, routes the generic Beta NTC divider and the unrelated Shockley diode to `adc.<id>.5_volts` / `adc.<id>.6_volts`, checks both solved voltages against independent references, and reads them back through that family's firmware register sequence. NTC codes must fall monotonically from -10 °C to 80 °C.

### GPIO inputs

[`cosim_onboarding_gpio_analog.rs`](../crates/core/tests/cosim_onboarding_gpio_analog.rs)::`every_onboarding_profile_with_a_gpio_input_takes_routed_ntc_and_diode_levels` covers every onboarding profile whose bus models a GPIO input. The port is the first peripheral the built bus reports as a GPIO input. The same Beta NTC divider and Shockley diode are routed to `board.gpio_in.<port>.0` / `.1` and their solved voltages are checked against independent references. The NTC pin has to follow a -10 → 25 → 80 → 25 → -10 °C sweep with Schmitt hysteresis, and the diode pin has to stay below VIL. Both levels are read back through `Peripheral::read_gpio_input` and through a firmware load from the port's input register. Thresholds are 0.3/0.7 × 3.3 V simulation assumptions, because no import records any. This is GPIO threshold coverage, not ADC support.

The test loads P1IN with a byte load and PAIN with a halfword load, as MSP430 firmware does (`mov.b &P1IN`), and pins P1IN at 0x20 and PAIN at 0x200. The descriptors also set `flash_boot_alias: false`: with the Cortex-M boot alias on, flash mirrored over 0x0000.. and hid the peripheral file, which made the `msp430f2619` load fail. Negative control, run locally: swapping `port8.yaml`'s IN and OUT offsets fails the firmware load on `msp430f2619:p1`. Not modelled: PxSEL / PxREN / PxDS, the P1/P2 interrupt registers, and port J. No MSP430 CPU is modelled either (`arch: unknown`; the Renode `msp430f2619` import says `arm`), so no firmware runs on these profiles yet. The proof is a bus load at the silicon address.

The Allwinner A20 and Renesas RZ/G2L imports (`a20`, `renesas_rz_g2l`) declared no GPIO: Renode's platforms for both leave the pin controller out. Neither port keeps its direction in a one-bit-per-pin enable register, and the router binds `board.gpio_in.<port>.<pin>` only to a pin it knows is an input. A20 holds direction in 4-bit `Pn_CFG` nibbles (0 input, 1 output, 2..6 functions, 7 disabled). RZ/G2L holds it in 2-bit `PM_m` pairs (01 input, 10 output, 11 output with input, 00 Hi-Z). Generic mechanism: a `GPIO` descriptor may now declare `gpio_mode` (`register`, `bits_per_pin`, `output` values, `input` values) in place of `ENABLE`. Pin k's field is bits k·w.. of the little-endian bytes starting at that register, so it runs on into the registers declared after it (`Pn_CFG1` holds pins 8..15). An `output` value drives the pad, an `input` value makes it a GPIO input, and any other value is a function. STM32 `MODER` has the same shape. Unit tests `declarative_gpio_mode_field_sets_direction_across_registers` and `declarative_gpio_mode_field_takes_several_output_values` cover both layouts. A descriptor with an `ENABLE` register is untouched, because `ENABLE` still wins. The A20 PIO sits at 0x01C2_0800 with one 0x24-byte bank per port, `Pn_CFG0..3` @+0x00, `Pn_DAT` @+0x10 (`sun7i-a20.dtsi` `pinctrl@1c20800`; Linux `pinctrl-sunxi.h` `BANK_MEM_SIZE`, `DATA_REGS_OFFSET`). Ports A..I run on `configs/peripherals/sunxi/pio.yaml`, and `Pn_DAT`, the register for both directions, is the IN register. The RZ/G2L controller sits at 0x1103_0000 (`r9a07g044.dtsi` `pinctrl@11030000`) with `P_m` @0x0000+off, `PM_m` @0x0100+2·off, `PMC_m` @0x0200+off and `PIN_m` @0x0800+off (Linux `pinctrl-rzg2l.c`); port 0 has off 0x10. It runs on `configs/peripherals/rzg2l/port.yaml` at byte width, and the test sets `PM` to 01 as `rzg2l_gpio_direction_input` does before it loads `PIN_0` with a byte load. The test pins PA_DAT at 0x01C2_0810 and PIN_0 at 0x1103_0810. Negative controls, run locally: moving the sunxi IN to `Pn_DRV0`, dropping its `gpio_mode`, setting RZ `PM` to output, or moving RZ `PIN` onto `P` each fail the test. Not modelled: the sunxi port has no separate output latch, so an output pin reports no driven level, and a firmware write to `Pn_DAT` stays until the next routed level replaces the input bits. Neither a function or disabled `Pn_CFG` nibble nor RZ `PM` 00 or `PMC` gates the pad. Only RZ port 0 is declared, because one window spans the other ports' bytes. RZ `PFC` / `IOLH` / `PUPD` and both parts' interrupt registers are not declared. A20 `CFG` resets to 0 (input); H3 and later reset it to 7 and need their own reset values.

The LiteX VexRiscv imports `litex_vexriscv` and `litex_vexriscv_micropython` declared no GPIO: Renode keeps the SoC's peripherals in an included `.repl` the import dropped, so only `clock0` (`litex_mmcm_csr32` at 0xE000_4800) and the Ethernet PHY survived. That clock base is the one the Zephyr `enjoydigital/litex_vexriscv` board declares, and the same board puts a LiteX `GPIOOut` at 0xE000_5800 (`port-is-output`) and a `GPIOIn` at 0xE000_6000 (`litex_vexriscv.dts`). `GPIOIn` (`litex/soc/cores/gpio.py`) is one read-only `in` CSR at the core base, pin k at bit k, which Zephyr reads with a single CSR load (`gpio_litex.c`). It has no output latch and no direction register, so the router had no way to know its pins are inputs. Generic mechanism: a `GPIO` descriptor with an `IN` register and no `ENABLE`, `gpio_mode` or `OUT` latch is now input-only on the declarative path, so every pin in range is an input. Unit test `declarative_gpio_without_output_latch_is_input_only` checks this and checks that adding an `OUT` latch makes the direction underivable again. Only `sunxi/pio.yaml` had an `IN` with no `OUT` before this change, and its `gpio_mode` is still consulted first. The two ports run on `configs/peripherals/litex/gpio_in.yaml` and `gpio_out.yaml`, and the test pins `in` at 0xE000_6000 on both profiles. `litex_linux_vexriscv_sdcard` already declared both cores as `litex_gpio`, which ran on the STM32F1 placeholder (IDR @0x08). It now uses the same two descriptors at its own bases (0xF000_4800 / 0xF000_7000), so its routed level is read at `in` @0x00, and `litex_gpio` leaves the placeholder list. For up to eight pins the value is in the low byte of the base word whether the SoC's CSR data width is 8 or 32 bits. Negative controls, run locally: moving `in` to +0x04 fails the firmware load, and giving `gpio_in.yaml` an `OUT` latch fails the router (`UnknownPad`). Not modelled: the `with_irq` event manager (Zephyr `irq_mode`/`irq_edge`/`irq_pend`/`irq_en` at +0x04..+0x14), and `GPIOOut` is storage only, so it drives no pad. `arty_litex_vexriscv` shares the clock base but drives its LEDs, switches and buttons through Renode's `LiteX_ControlAndStatus` (`cas`), whose base the import does not record, so it is still uncovered. Onboarding chips are not scanned by `scripts/gen_embedded_descriptors.py`, so these descriptors load from the filesystem and are not in the wasm build.

The NXP Vybrid and Toradex Colibri VF61 imports had no GPIO: Renode's `vybrid` platform leaves it out. The VF6xx GPIO module puts GPIO0..GPIO4 at 0x400F_F000 + 0x40·n (Linux `vf610.dtsi`, the second `reg` of each gpio node; the first is its PORT block at 0x4004_9000 + 0x1000·n) with the Kinetis register set, PDOR/PSOR/PCOR/PTOR at +0x00..+0x0C and PDIR at +0x10 (VFxxx RM ch. 7; `gpio-vf610.c` `GPIO_PDIR`). They now run on `profile: kinetis`, the map the promoted `configs/chips/mk64f12.yaml` already uses, with no model code change. Negative control, run locally: pointing `gpio/kinetis` at PDOR (0x00) fails on `colibri-vf61:gpio0`. Not modelled: Vybrid has no PDDR (+0x14), and direction and the input buffer live in the IOMUXC pad register (OBE/IBE), which is not declared, so PDIR reads the pad whatever IBE says and the model also answers PDDR. The PORT blocks (pin interrupts) are not declared either.

The nRF52840-DK and Nano 33 BLE descriptors based GPIO0/GPIO1 at OUT (0x5000_0500 / 0x5000_0800) with no `reg_offset`. That put IN at 0x5000_0A10, inside the next port's window. They now declare `reg_offset: 0x500`, the same fix as `configs/chips/nrf52833.yaml`. The test fails if any count changes, if an unclassified GPIO type appears, or if a listed register gap starts tracking.

### simavr AVR profiles

The simavr imports used to carry `peripherals: []`. [`cosim_onboarding_avr_analog.rs`](../crates/core/tests/cosim_onboarding_avr_analog.rs)::`every_simavr_profile_on_a_modelled_avr_core_converts_ntc_and_diode_in_firmware` covers the parts whose register map is one LabWired's AVR cores run. The map was checked against each part's avr-libc 2.0.0 `io*.h`: PINx/DDRx/PORTx, ADCL/ADCH 0x78/0x79, ADCSRA 0x7A, ADCSRB 0x7B, ADMUX 0x7C. Those descriptors now declare the same `avr_gpio` port mirrors, `avr_adc` input window and `analog_pins` as the in-tree ATmega328P/1281/2560 descriptors. The classic ATmega8/16/32 run on their own I/O-space cores (`AvrModel::Atmega8/16/32`): ADCL/ADCH 0x24/0x25, ADCSRA 0x26, ADMUX 0x27, ports ascending from 0x30, SRAM from 0x60, and the `avr_adc` window at 0x1_0060. They have no ADCSRB, so the test converts with STS ADMUX/ADCSRA there, and it also checks the internal 2.56 V reference (REFS = 11) and the 1.30 V (ATmega8, MUX 0x0E) or 1.22 V (16/32, MUX 0x1E) bandgap. The ATmega164/324/644/1284P run on the port-A cores (`AvrModel::Atmega164/324/644/1284`): avr-libc `iomxx4.h`/`iom324p.h`/`iom644.h`/`iom1284p.h` place every 328P register at the 328P's address and add PINA/DDRA/PORTA at 0x20..0x22. Their ADC is ADC0..7 on PA0..PA7 with MUX4:0, so the test also checks REFS = 10 (internal 1.1 V), REFS = 11 (internal 2.56 V), the MUX 0x1E bandgap, and that the 328P's bandgap code 0x0E reads 0 there. The ATmega128RFA1/128RFR2 run on the RF core (`AvrModel::Atmega128Rf`): avr-libc `iom128rfa1.h`/`iom128rfr2.h` keep the 1281's ports A..G and ADC registers (0x100..0x10B is empty, no ports H..L), with 16 KB SRAM to 0x41FF. Their ADC is powered from the internal 1.8 V AVDD regulator (datasheets 8266F and 8393C, chapter 27), so codes are against 1.8 V and the NTC divider clips at 0x3FF below 0 °C. The test also checks REFS = 10 (internal 1.5 V), REFS = 11 (internal 1.6 V), the 1.2 V VBG on MUX 0x1E, AVSS on 0x1F, and a firmware poll of ADCSRB.AVDDOK/REFOK (0 before ADEN, 1 after). The ATtiny25/45/85 run on the ATtiny x5 cores (`AvrModel::Attiny25/45/85`): avr-libc `iotn25.h`/`iotn45.h`/`iotn85.h` (`iotnx5.h`) keep ADCL..ADMUX at the classic 0x24..0x27 and PINB/DDRB/PORTB at 0x36..0x38 (port B is the only port), with SRAM from 0x60 to RAMEND 0xDF/0x15F/0x25F and PUD in MCUCR bit 6. Their ADC is ADC0..3 on PB5, PB2, PB4, PB3 (datasheet 2586Q Table 17-4), and ADMUX bit 4 is REFS2, not MUX4. So the test also checks REFS2:0 = 010 (internal 1.1 V) and 110 (internal 2.56 V), the 1.1 V bandgap on MUX 0x0C, and that 0x04 (differential), 0x0D (GND), 0x0E and 0x0F (temperature sensor, not modelled) read 0. GPIO thresholds are VIL 0.3 / VIH 0.6 VCC (Table 21-1, VCC 2.4..5.5 V). The ATtiny24/44/84 run on the ATtiny x4 cores (`AvrModel::Attiny24/44/84`): avr-libc `iotn24.h`/`iotn44.h`/`iotn84.h` (`iotnx4.h`) keep ADCSRB..ADMUX at 0x23..0x27, add PINA/DDRA/PORTA at 0x39..0x3B beside port B at 0x36..0x38, and share the x5 parts' SRAM, flash and MCUCR.PUD. Their ADC is ADC0..7 on PA0..PA7 (datasheet 8183F Table 16-4) with a six-bit MUX5:0 in ADMUX, so ADLAR moves to ADCSRB bit 4. The test checks REFS = 10 (internal 1.1 V), the 1.1 V bandgap on MUX 0x21, that 0x08, 0x0C, 0x1E, 0x20 (AGND) and 0x22 (temperature sensor, not modelled) read 0, and that firmware setting ADCSRB.ADLAR reads a left-adjusted diode code. The ATmega128 runs on its own I/O-space core (`AvrModel::Atmega128`): avr-libc `iom128.h` keeps ADCL..ADMUX at 0x24..0x27 (no ADCSRB) and ports A..D at the classic 0x30..0x3B, adds port E at 0x21..0x23 and port G at 0x63..0x65, and splits port F (PINF 0x20, DDRF/PORTF 0x61/0x62), with extended I/O at 0x60..0xFF, SRAM 0x100..0x10FF and SFIOR.PUD at 0x40. Port F is mirrored on the bus at 0x1_0100 (PINF, DDRF, PORTF) and the `avr_adc` window sits at 0x1_0200. Its ADC is ADC0..7 on PF0..PF7 with MUX4:0, so the test also checks the internal 2.56 V reference (REFS = 11) and the 1.23 V bandgap on MUX 0x1E. The ATtiny13 runs on its own I/O-space core (`AvrModel::Attiny13`): avr-libc `iotn13.h` keeps the x5 parts' ADCSRB..ADMUX at 0x23..0x27, PINB/DDRB/PORTB at 0x36..0x38 and MCUCR.PUD, with 1 KB flash and SRAM 0x60..0x9F. Its ADMUX has only REFS0 (bit 6), ADLAR and MUX1:0, so ADC0..3 are PB5, PB2, PB4, PB3 (ATtiny13A datasheet 8126F §14.12.1) and there is no bandgap input. The test checks REFS0 selecting the internal 1.1 V (on the megas that bit pattern is AVcc), that bit 7 (the x5 parts' REFS1) leaves VCC the reference, and that the x5 bandgap code 0x0C reads ADC0. The ATmega32U4 (Arduino Leonardo/Micro) runs on its own core (`AvrModel::Atmega32u4`): avr-libc `iom32u4.h` keeps the 328P's ADCL..ADMUX at 0x78..0x7C, Timer0/1, SPI, TWI and MCUCR.PUD, has ports B..F at 0x23..0x31 (no port A), SRAM 0x100..0xAFF and 32 KB flash, and its vector table is the 1281's up to EE READY with TWI at slot 37 and SPM READY at 38. Its ADC has no ADC2/ADC3: ADC0/1 and ADC4..7 are on port F and ADC8..13 on PD4, PD6, PD7, PB4, PB5, PB6 (datasheet 7766 §24.9), and MUX5 is ADCSRB bit 5, not the 2560's bit 3. The `avr_adc` window is indexed by ADC number. The diode routes to PB6/ADC13, so the test checks that ADCSRB bit 5 reaches it and bit 3 leaves ADC5, that MUX 0x02 reads 0, the internal 2.56 V reference (REFS = 11) and the 1.1 V bandgap on MUX 0x1E. The ATtiny1634 runs on its own I/O-space core (`AvrModel::Attiny1634`): avr-libc `iotn1634.h` puts ADCL/ADCH at 0x20/0x21, ADCSRB 0x22, ADCSRA 0x23 and ADMUX 0x24, and its ports are PINx/DDRx/PORTx/PUEx groups (C 0x27..0x2A, B 0x2B..0x2E, A 0x2F..0x32), with extended I/O at 0x60..0xFF, SRAM 0x100..0x4FF and 16 KB flash. Pull-ups follow PUEx, not PORTx, and there is no PUD, so the PORTx byte mirrored to each `avr_gpio` window is `(PORTx & DDRx) | (PUEx & !DDRx)`. Its ADC is ADC0..11 on PA3..PA7, PB0..PB3, PC0..PC2 (datasheet 8303 §19.13.1; simavr `sim_tiny1634.h` maps the same 12 single-ended codes and 0x0F to GND) with MUX3:0, so the diode on PC2/ADC11 needs no MUX5. The test checks REFS = 10 (internal 1.1 V), that REFS = 01 (AREF) stays VCC, that 0x0C..0x0F read 0, and that ADLAR is ADCSRB bit 3: bit 4 (the x4's ADLAR) and ADMUX bit 5 (REFEN here, ADLAR on the megas) leave the result right-adjusted. The ATmega16M1/64M1 run on the M1 cores (`AvrModel::Atmega16m1/64m1`): avr-libc `iom16m1.h`/`iom64m1.h` (identical but for memory sizes) keep the 328P's ADCL..ADMUX at 0x78..0x7C, Timer0/1, SPI and MCUCR.PUD, with ports B..E at 0x23..0x2E (no port A), SRAM 0x100..0x4FF (16M1) or 0x10FF (64M1) and 16/64 KB flash. Their vector table puts the four comparators, the PSC and INT0..3 first, so Timer1 starts at slot 12 and the ADC is slot 28 (`m1_vector`). Their ADC is ADC0..10 on PE2, PD4, PD5, PD6, PB7, PB2, PB5, PB6, PC4, PC5, PC6 (datasheet 8209F §1.2, Table 22-5) with MUX4:0 and no MUX5 (ADCSRB bit 5 is AREFEN). So the diode on PC6/ADC10 needs no ADCSRB bit, and the test checks that ADCSRB bits 3 and 5 leave the channel alone, the internal 2.56 V reference (REFS = 11), the 1.1 V bandgap on MUX 0x11, VCC/4 on 0x0C, GND on 0x12, and that the 328P (0x0E) and mega (0x1E) bandgap codes read 0. GPIO thresholds are VIL 0.2 / VIH 0.6 VCC (Table 29-1). The PSC, CAN, LIN, the four comparators, the amplifiers, the DAC and the current source are not modelled. The ATmega169P/169PA (AVR Butterfly) run on their own core (`AvrModel::Atmega169p`): avr-libc `iom169p.h`/`iom169pa.h` keep the 328P's Timer1, USART0, SPI, EEPROM, MCUCR.PUD and ADCL..ADMUX at 0x78..0x7C, with ports A..G at 0x20..0x34 (the 1281's addresses), SRAM 0x100..0x4FF and 16 KB flash, and their own vector table (`m169p_vector`: ADC slot 20). Their ADC is ADC0..7 on PF0..PF7 with MUX4:0 and no MUX5 (datasheet 8018P Table 22-4). It is the first AVR core here with differential inputs: 0x10..0x17 are ADC0..7 minus ADC1 and 0x18..0x1D ADC0..5 minus ADC2, gain 1, giving `(Vpos - Vneg) * 512 / Vref` as a signed 10-bit result, -512..511 (§22.7; the datasheet example of 300 mV - 500 mV at 1.1 V reads 0x3A3 = -93, and it is a unit test). A second session routes the NTC divider to PF0 and the diode to PF1, and firmware converts MUX 0x10 at every temperature. The result is NTC minus diode, so it turns negative between 50 °C and 80 °C and saturates at +511 against 1.1 V when cold. MUX 0x19 puts the diode against the undriven ADC2. The test also checks REFS = 11 (internal 1.1 V), the MUX 0x1E bandgap, MUX 0x1F GND, that 0x08..0x0F (0x0E is the 328P's bandgap code) are N/A, and that ADCSRB bit 3 is not MUX5. GPIO thresholds are VIL 0.3 / VIH 0.6 VCC (§28.2, VCC 2.4..5.5 V). The LCD controller, USI and Timer0/2 are not modelled: the 169P keeps Timer0/2 clock select in TCCRnA, so they do not count. INT0 and PCINT0..15 are stored only. Every conversion is read back with LDS ADCL/ADCH. The generic Beta NTC divider routes to the lowest ADC pad and the Shockley diode to the highest, through `board.analog.<pad>_volts`. The CPU core the descriptor name selects converts both with an STS ADCSRB/ADMUX/ADCSRA sequence. PK7/ADC15 on the 100-pin megas and PB6/ADC13 on the 32U4 exercise ADCSRB.MUX5. Codes must equal `mV * 1024 / AVcc` (5 V, or 1.8 V AVDD on the RF parts), and the NTC code must fall monotonically from -10 °C to 80 °C wherever it is below full scale.
