# Mixed-signal board coverage

This inventory tracks every system profile in `configs/systems/*.yaml` (including demos,
fixtures, and multiple profiles for the same physical board). A profile is covered only when
a board-specific test solves an analog device/netlist, routes it to a modeled board endpoint,
and asserts the result. Endpoints include an ADC conversion or a voltage-thresholded digital
input on profiles without an ADC or without an externally routable ADC input. A GPIO-only proof
does not imply ADC support. Generic chip bus tests, analog output traces without a board endpoint,
and device-only unit tests do not count.

Current inventory: **103 top-level profiles; 103 have end-to-end analog coverage; 0 have no end-to-end analog coverage.** The 26 exact-part profiles in `configs/systems/stm32-catalog/` are also covered (see [STM32 catalog profiles](#stm32-catalog-profiles)). Of the 245 imported profiles in `configs/systems/onboarding/`, 221 are covered end to end through a GPIO input (24 of them also through every ADC instance they declare, 30 simavr AVR parts also through a firmware conversion on their CPU-owned ADC, and the 3 ATtiny2313/2313A/4313 and the AT90USB162 through their analog comparator), 3 more (`stm32h7`, `stm32h747`, `stm32h747-disco`) only through their ADCs, and 21 have neither a wired GPIO input nor a convertible ADC (see [Onboarding profiles](#onboarding-profiles)). Each round selects the next uncovered profile and extends shared device, netlist, or routing support where needed. Coverage through GPIO thresholds does not imply ADC support.

The MPC5567 import (`mpc5567`) declared its two eSCI UARTs, FEC, eMIOS and an FMPLL Python stub, but no GPIO. Renode's `mpc5567.repl` does not declare the System Integration Unit. The MPC5567 reference manual (ch. 6, "System Integration Unit") and the MPC55xx device header's `struct SIU_tag` put the SIU at 0xC3F9_0000, the 16 KB slot between FMPLL (0xC3F8_0000, which the import already uses) and eMIOS (0xC3FA_0000). Each pad n has a 16-bit `PCRn` at +0x040 + 2n, an output byte `GPDOn` at +0x600 + n and an input byte `GPDIn` at +0x800 + n, with the data in bit 0. The declarative GPIO path put pin k at bit k only, so it could not describe a byte per pad. Generic mechanism: `PeripheralDescriptor` gains `gpio_pin_stride` (default 1). Pin k of `IN`, `OUT` and `ENABLE` is bit `k * gpio_pin_stride`, and the port has `width / stride` pins. Every existing descriptor leaves it unset, so its pin positions are unchanged. The unit test `declarative_gpio_pin_stride_gives_each_pin_its_own_byte` covers stride 8 on IN, OUT and ENABLE. The new `configs/peripherals/mpc5500/siu_gpio.yaml` declares `GPDI0..3` as one 32-bit `IN` at stride 8, so it covers GPIO[0..3]. A byte register reads the same on the big-endian e200 core and on LabWired's little-endian bus. The test reads each pad with its own byte load, as `SIU.GPDI[n].B.PDI` firmware does, and `SILICON_INPUT_ADDRESS` pins `GPDI0` at 0xC3F9_0800. The main test cannot catch a wrong pad position: it puts the NTC on pad 0, which is bit 0 at any stride, and the diode pad never leaves 0. `ntc_on_the_second_input_pad_lands_at_that_pads_register_bit` therefore swaps them for the ports in `NON_UNIT_PAD_POSITION`, and the NTC must then toggle `GPDI1`. Negative controls, run locally: with `gpio_pin_stride` removed, the main test still passes (the gap above), while the swapped test fails with `mpc5567:siu: firmware load from 0xc3f90800 must track both pins`. Not modelled: GPIO[4..] (a declarative register is at most 32 bits), output drive (direction is `PCRn.OBE`, one bit of a 16-bit field per pad, which `gpio_mode` cannot express, so `GPDO` is storage only), `PCR.IBE` gating, function select, pulls, the per-pad PCR reset values (0 here), and the SIU interrupt and reset registers. The import also still says `arch: arm` for this e200z6 PowerPC part.

The UP Squared import (`up_squared_x86_64`) declared an NS16550 UART, the HPET and Renode's PCI Python stub, but no GPIO: Renode's `up_squared_x86_64.repl` leaves the Apollo Lake pin controller out. Apollo Lake puts its four GPIO communities in the P2SB sideband window at 0xD000_0000 | PID << 16, so the north community (`PID_GPIO_N` 0xC5, coreboot `apollolake/pcr_ids.h`) is at 0xD0C5_0000, which is also Zephyr's `apollo_lake.dtsi` `gpio_n_000_031: gpio@d0c50000`. The chip file still says `arch: arm`, as the import wrote it; the analog path does not depend on the core.

### simavr AVR profiles

The simavr imports used to carry `peripherals: []`. [`cosim_onboarding_avr_analog.rs`](../crates/core/tests/cosim_onboarding_avr_analog.rs)::`every_simavr_profile_on_a_modelled_avr_core_converts_ntc_and_diode_in_firmware` covers the parts whose register map is one LabWired's AVR cores run. The map was checked against each part's avr-libc 2.0.0 `io*.h`: PINx/DDRx/PORTx, ADCL/ADCH 0x78/0x79, ADCSRA 0x7A, ADCSRB 0x7B, ADMUX 0x7C. Those descriptors now declare the same `avr_gpio` port mirrors, `avr_adc` input window and `analog_pins` as the in-tree ATmega328P/1281/2560 descriptors. The classic ATmega8/16/32 run on their own I/O-space cores (`AvrModel::Atmega8/16/32`): ADCL/ADCH 0x24/0x25, ADCSRA 0x26, ADMUX 0x27, ports ascending from 0x30, SRAM from 0x60, and the `avr_adc` window at 0x1_0060. They have no ADCSRB, so the test converts with STS ADMUX/ADCSRA there, and it also checks the internal 2.56 V reference (REFS = 11) and the 1.30 V (ATmega8, MUX 0x0E) or 1.22 V (16/32, MUX 0x1E) bandgap. The ATmega164/324/644/1284P run on the port-A cores (`AvrModel::Atmega164/324/644/1284`): avr-libc `iomxx4.h`/`iom324p.h`/`iom644.h`/`iom1284p.h` place every 328P register at the 328P's address and add PINA/DDRA/PORTA at 0x20..0x22. Their ADC is ADC0..7 on PA0..PA7 with MUX4:0, so the test also checks REFS = 10 (internal 1.1 V), REFS = 11 (internal 2.56 V), the MUX 0x1E bandgap, and that the 328P's bandgap code 0x0E reads 0 there. The ATmega128RFA1/128RFR2 run on the RF core (`AvrModel::Atmega128Rf`): avr-libc `iom128rfa1.h`/`iom128rfr2.h` keep the 1281's ports A..G and ADC registers (0x100..0x10B is empty, no ports H..L), with 16 KB SRAM to 0x41FF. Their ADC is powered from the internal 1.8 V AVDD regulator (datasheets 8266F and 8393C, chapter 27), so codes are against 1.8 V and the NTC divider clips at 0x3FF below 0 °C. The test also checks REFS = 10 (internal 1.5 V), REFS = 11 (internal 1.6 V), the 1.2 V VBG on MUX 0x1E, AVSS on 0x1F, and a firmware poll of ADCSRB.AVDDOK/REFOK (0 before ADEN, 1 after). The ATtiny25/45/85 run on the ATtiny x5 cores (`AvrModel::Attiny25/45/85`): avr-libc `iotn25.h`/`iotn45.h`/`iotn85.h` (`iotnx5.h`) keep ADCL..ADMUX at the classic 0x24..0x27 and PINB/DDRB/PORTB at 0x36..0x38 (port B is the only port), with SRAM from 0x60 to RAMEND 0xDF/0x15F/0x25F and PUD in MCUCR bit 6. Their ADC is ADC0..3 on PB5, PB2, PB4, PB3 (datasheet 2586Q Table 17-4), and ADMUX bit 4 is REFS2, not MUX4. So the test also checks REFS2:0 = 010 (internal 1.1 V) and 110 (internal 2.56 V), the 1.1 V bandgap on MUX 0x0C, and that 0x04 (differential), 0x0D (GND), 0x0E and 0x0F (temperature sensor, not modelled) read 0. GPIO thresholds are VIL 0.3 / VIH 0.6 VCC (Table 21-1, VCC 2.4..5.5 V). The ATtiny24/44/84 run on the ATtiny x4 cores (`AvrModel::Attiny24/44/84`): avr-libc `iotn24.h`/`iotn44.h`/`iotn84.h` (`iotnx4.h`) keep ADCSRB..ADMUX at 0x23..0x27, add PINA/DDRA/PORTA at 0x39..0x3B beside port B at 0x36..0x38, and share the x5 parts' SRAM, flash and MCUCR.PUD. Their ADC is ADC0..7 on PA0..PA7 (datasheet 8183F Table 16-4) with a six-bit MUX5:0 in ADMUX, so ADLAR moves to ADCSRB bit 4. The test checks REFS = 10 (internal 1.1 V), the 1.1 V bandgap on MUX 0x21, that 0x08, 0x0C, 0x1E, 0x20 (AGND) and 0x22 (temperature sensor, not modelled) read 0, and that firmware setting ADCSRB.ADLAR reads a left-adjusted diode code. The ATmega128 runs on its own I/O-space core (`AvrModel::Atmega128`): avr-libc `iom128.h` keeps ADCL..ADMUX at 0x24..0x27 (no ADCSRB) and ports A..D at the classic 0x30..0x3B, adds port E at 0x21..0x23 and port G at 0x63..0x65, and splits port F (PINF 0x20, DDRF/PORTF 0x61/0x62), with extended I/O at 0x60..0xFF, SRAM 0x100..0x10FF and SFIOR.PUD at 0x40. Port F is mirrored on the bus at 0x1_0100 (PINF, DDRF, PORTF) and the `avr_adc` window sits at 0x1_0200. Its ADC is ADC0..7 on PF0..PF7 with MUX4:0, so the test also checks the internal 2.56 V reference (REFS = 11) and the 1.23 V bandgap on MUX 0x1E. The ATtiny13 runs on its own I/O-space core (`AvrModel::Attiny13`): avr-libc `iotn13.h` keeps the x5 parts' ADCSRB..ADMUX at 0x23..0x27, PINB/DDRB/PORTB at 0x36..0x38 and MCUCR.PUD, with 1 KB flash and SRAM 0x60..0x9F. Its ADMUX has only REFS0 (bit 6), ADLAR and MUX1:0, so ADC0..3 are PB5, PB2, PB4, PB3 (ATtiny13A datasheet 8126F §14.12.1) and there is no bandgap input. The test checks REFS0 selecting the internal 1.1 V (on the megas that bit pattern is AVcc), that bit 7 (the x5 parts' REFS1) leaves VCC the reference, and that the x5 bandgap code 0x0C reads ADC0. The ATmega32U4 (Arduino Leonardo/Micro) runs on its own core (`AvrModel::Atmega32u4`): avr-libc `iom32u4.h` keeps the 328P's ADCL..ADMUX at 0x78..0x7C, Timer0/1, SPI, TWI and MCUCR.PUD, has ports B..F at 0x23..0x31 (no port A), SRAM 0x100..0xAFF and 32 KB flash, and its vector table is the 1281's up to EE READY with TWI at slot 37 and SPM READY at 38. Its ADC has no ADC2/ADC3: ADC0/1 and ADC4..7 are on port F and ADC8..13 on PD4, PD6, PD7, PB4, PB5, PB6 (datasheet 7766 §24.9), and MUX5 is ADCSRB bit 5, not the 2560's bit 3. The `avr_adc` window is indexed by ADC number. The diode routes to PB6/ADC13, so the test checks that ADCSRB bit 5 reaches it and bit 3 leaves ADC5, that MUX 0x02 reads 0, the internal 2.56 V reference (REFS = 11) and the 1.1 V bandgap on MUX 0x1E. The ATtiny1634 runs on its own I/O-space core (`AvrModel::Attiny1634`): avr-libc `iotn1634.h` puts ADCL/ADCH at 0x20/0x21, ADCSRB 0x22, ADCSRA 0x23 and ADMUX 0x24, and its ports are PINx/DDRx/PORTx/PUEx groups (C 0x27..0x2A, B 0x2B..0x2E, A 0x2F..0x32), with extended I/O at 0x60..0xFF, SRAM 0x100..0x4FF and 16 KB flash. Pull-ups follow PUEx, not PORTx, and there is no PUD, so the PORTx byte mirrored to each `avr_gpio` window is `(PORTx & DDRx) | (PUEx & !DDRx)`. Its ADC is ADC0..11 on PA3..PA7, PB0..PB3, PC0..PC2 (datasheet 8303 §19.13.1; simavr `sim_tiny1634.h` maps the same 12 single-ended codes and 0x0F to GND) with MUX3:0, so the diode on PC2/ADC11 needs no MUX5. The test checks REFS = 10 (internal 1.1 V), that REFS = 01 (AREF) stays VCC, that 0x0C..0x0F read 0, and that ADLAR is ADCSRB bit 3: bit 4 (the x4's ADLAR) and ADMUX bit 5 (REFEN here, ADLAR on the megas) leave the result right-adjusted. The ATmega16M1/64M1 run on the M1 cores (`AvrModel::Atmega16m1/64m1`): avr-libc `iom16m1.h`/`iom64m1.h` (identical but for memory sizes) keep the 328P's ADCL..ADMUX at 0x78..0x7C, Timer0/1, SPI and MCUCR.PUD, with ports B..E at 0x23..0x2E (no port A), SRAM 0x100..0x4FF (16M1) or 0x10FF (64M1) and 16/64 KB flash. Their vector table puts the four comparators, the PSC and INT0..3 first, so Timer1 starts at slot 12 and the ADC is slot 28 (`m1_vector`). Their ADC is ADC0..10 on PE2, PD4, PD5, PD6, PB7, PB2, PB5, PB6, PC4, PC5, PC6 (datasheet 8209F §1.2, Table 22-5) with MUX4:0 and no MUX5 (ADCSRB bit 5 is AREFEN). So the diode on PC6/ADC10 needs no ADCSRB bit, and the test checks that ADCSRB bits 3 and 5 leave the channel alone, the internal 2.56 V reference (REFS = 11), the 1.1 V bandgap on MUX 0x11, VCC/4 on 0x0C, GND on 0x12, and that the 328P (0x0E) and mega (0x1E) bandgap codes read 0. GPIO thresholds are VIL 0.2 / VIH 0.6 VCC (Table 29-1). The PSC, CAN, LIN, the four comparators, the amplifiers, the DAC and the current source are not modelled. The ATmega169P/169PA (AVR Butterfly) run on their own core (`AvrModel::Atmega169p`): avr-libc `iom169p.h`/`iom169pa.h` keep the 328P's Timer1, USART0, SPI, EEPROM, MCUCR.PUD and ADCL..ADMUX at 0x78..0x7C, with ports A..G at 0x20..0x34 (the 1281's addresses), SRAM 0x100..0x4FF and 16 KB flash, and their own vector table (`m169p_vector`: ADC slot 20). Their ADC is ADC0..7 on PF0..PF7 with MUX4:0 and no MUX5 (datasheet 8018P Table 22-4). It is the first AVR core here with differential inputs: 0x10..0x17 are ADC0..7 minus ADC1 and 0x18..0x1D ADC0..5 minus ADC2, gain 1, giving `(Vpos - Vneg) * 512 / Vref` as a signed 10-bit result, -512..511 (§22.7; the datasheet example of 300 mV - 500 mV at 1.1 V reads 0x3A3 = -93, and it is a unit test). A second session routes the NTC divider to PF0 and the diode to PF1, and firmware converts MUX 0x10 at every temperature. The result is NTC minus diode, so it turns negative between 50 °C and 80 °C and saturates at +511 against 1.1 V when cold. MUX 0x19 puts the diode against the undriven ADC2. The test also checks REFS = 11 (internal 1.1 V), the MUX 0x1E bandgap, MUX 0x1F GND, that 0x08..0x0F (0x0E is the 328P's bandgap code) are N/A, and that ADCSRB bit 3 is not MUX5. GPIO thresholds are VIL 0.3 / VIH 0.6 VCC (§28.2, VCC 2.4..5.5 V). The LCD controller, USI and Timer0/2 are not modelled: the 169P keeps Timer0/2 clock select in TCCRnA, so they do not count. INT0 and PCINT0..15 are stored only. Every conversion is read back with LDS ADCL/ADCH. The generic Beta NTC divider routes to the lowest ADC pad and the Shockley diode to the highest, through `board.analog.<pad>_volts`. The CPU core the descriptor name selects converts both with an STS ADCSRB/ADMUX/ADCSRA sequence. PK7/ADC15 on the 100-pin megas and PB6/ADC13 on the 32U4 exercise ADCSRB.MUX5. Codes must equal `mV * 1024 / AVcc` (5 V, or 1.8 V AVDD on the RF parts), and the NTC code must fall monotonically from -10 °C to 80 °C wherever it is below full scale.

AVcc is the core's fixed 5 V reference, and the 0.3/0.6 VCC GPIO thresholds (0.2/0.6 VCC on the classic ATmega8/16/32) are the datasheet DC limits. The classic cores model only the map, the ports and the ADC; their timers, USART, SPI and TWI registers are stored only, and they take no interrupts. The port-A cores share the 328P's timers, USART0, SPI and TWI and enter their own vector slots, but INTn/PCINT, output-compare pads and USART1 are stored only. RAM size and SP reset follow the selected core, not the smaller parts' datasheets (ATmega48: 512 B). That does not affect the conversion path tested here.
