# LPC2294 validation status

## Current status

The LPC2294 is present in the imported Renode inventory, but it has no valid
boot or smoke evidence in LabWired. Its scoreboard entry is `not_run`; the
current inventory records 245 descriptors, 165 platforms booted, 165 booted
and smoke-passing, and 80 not run.

The imported descriptor identifies an ARM7TDMI-S / ARMv4T target. LabWired has
no ARM7 CPU implementation. `arch: arm` alone does not make this an ARM7
machine: the current ARM builder only accepts a `cortex-m*` core here, and
rejects `arm7tdmi-s`.

## Bounded descriptor

The chip profile names `core: arm7tdmi-s` and retains only the two imported
UART windows backed by the engine's generic `ns16550` model. It omits the four
`lpc_can` windows because they resolve to zero-answering stubs, and omits
`lpc_ctimer` because the engine has no registered model for it. The profile is
not marked verified; the UART mappings have not been exercised on this target.
The imported flash and RAM ranges also remain unverified.

The earlier generated validation report is not ARM7 evidence. It loaded
`uart-ok-thumbv7m.elf`, started the Cortex-M simulator, and faulted on a memory
access at `0x2001ffe0` after two instructions. That incorrect fixture run is
not counted as a boot in the Renode onboarding scoreboard.

## Next work

A real ARM7TDMI/ARMv4T CPU implementation is required before this descriptor
can be run honestly. No substitute CPU or peripheral stub was added in this
round. The existing not-run inventory metric remains under
`docs/coverage/renode-onboarding/metrics/lpc2294/`.
