# RP2350 (Raspberry Pi Pico 2)

The RP2350 (dual Cortex-M33, 4 MB XIP flash on the Pico 2 board, 520 KB SRAM) is onboarded as a
descriptor-level derivative of the RP2040 lane: it reuses the RP2040
behavioural models for UART (PL011), I2C, SPI, DMA, PIO (v1-compatible on
PIO0–2), SIO, ADC, PWM, timer, and watchdog, with a `profile: rp2350` on the
shared clock/reset model for the moved APB map. It is **smoke-validated, not
hardware-validated** — no Pico 2 has been on the bench.

This page is the **Pico 2 carrier** (user LED GP25). The USB-C castellated
module is **[Waveshare RP2350-Zero](rp2350-zero.md)** (WS2812 on GP16).
The **[Adafruit Feather RP2350 with HSTX](adafruit-feather-rp2350.md)** is a
separate 8 MiB carrier profile; it currently claims only UART0 and the D13
GPIO7 LED smoke, not HSTX or the onboard NeoPixel.

The Raspberry Pi Pico 2 W + BME280 profile is a separate RP2350 carrier
example. It exercises I2C0 on GP4/GP5 and leaves the CYW43439 wireless module
and its WL_GPIO0 user LED outside the modeled scope; see
[examples/rpi-pico-2-w-bme280](../../examples/rpi-pico-2-w-bme280/README.md).

For Pico 2 build/run instructions, see
[`examples/pico2/README.md`](../../examples/pico2/README.md).
Zero: [`examples/rp2350-zero/README.md`](../../examples/rp2350-zero/README.md).

## Modeled (from chip yaml)

SYSINFO (CHIP_ID reads `0x30005927`; PART not in the datasheet, unverified), CLOCKS/RESETS/XOSC/PLL_SYS/PLL_USB/ROSC
(`rp2350` clkrst profile), UART0/1 (PL011), SPI0/1, I2C0/1, ADC, PWM,
TIMER0, WATCHDOG, DMA, PIO0/1/2 (v1 instruction set), SIO (core 0),
XIP_CTRL (declarative), POWERMAN/TICKS/TBMAN stubs, SysTick, NVIC.
Boot ROM API window at 0x00000000 (clean-room, `crates/core/roms/rp2350/`:
`rom_table_lookup` at the well-known 0x16 pointer, bootrom_state_reset,
get_sys_info CHIP_INFO, reboot NORMAL, the cacheless XIP-state operations,
flash_range_erase/program and writable flash_devinfo16_ptr), BOOTRAM (1 KB + WRITE_ONCE + BOOTLOCK0..7), USBCTRL
(RP2040 controller model on USBCTRL_IRQ 14; arduino-pico's TinyUSB CDC
enumerates against the simulated host and its `Serial` output is what the
Arduino matrix captures).
Double-precision coprocessor (DCP, p4/p5, datasheet 3.6.2): a sequence-level
model of the pico-sdk canned instruction sequences
(`crates/core/src/cpu/cortex_m/rp2350_dcp.rs`) — double/float add, sub,
mul, div, sqrt, compares and int/float/double conversions give IEEE-754
round-to-nearest-even results with denormals flushed to zero; engaged flag
and state save/restore follow the SDK's saving wrapper. `ddiv_fast` /
`sqrt_fast` return the correctly rounded value (silicon: < 0.5 ulp before
rounding); NaN results are the default NaN; RXVD (dclassify) faults.
GPIO coprocessor (GPIOC, p0, datasheet 3.6.1): every `gpio_coproc.h`
encoding runs as the equivalent SIO GPIO access
(`crates/core/src/cpu/cortex_m/rp2350_gpioc.rs`); pico-sdk `gpio_put` /
`gpio_set_dir`, and so arduino-pico `pinMode`/`digitalWrite`, use it.
TIMER0 and SIO use their RP2350 register maps (`profile: rp2350`): TIMER
INTR/INTE/INTF/INTS sit at 0x3c–0x48 behind LOCKED/SOURCE (storage only),
and every SIO GPIO register has a HI twin at +4 (only GPIO 0..29 modelled;
HI registers read 0).
SCS ACTLR (0xE000E008) as a plain register. SYSINFO at the RP2350 offsets
(PACKAGE_SEL 0x04 = QFN60, PLATFORM 0x08 = ASIC).

## RP2354B package derivative

[`configs/chips/rp2354b.yaml`](../../configs/chips/rp2354b.yaml) keeps the
QFN80 RP2354B identity: 48 GPIO pads, 520 KiB SRAM, 2 MiB stacked flash and
`SYSINFO.PACKAGE_SEL = 0`. It shares the same modeled core and peripheral
implementations. It does not inherit a physical hardware qualification.
The B-package descriptor maps CLOCKS, PSM, RESETS, IO_BANK0, IO_QSPI,
PADS_BANK0, PADS_QSPI, XOSC and both PLLs as separate 4 KiB register
windows from `addressmap.h`. Clock/reset ready bits use the existing model.
PSM and pad/QSPI registers remain storage only; power sequencing, pad
isolation and drive-strength effects are not implemented. The new map does
not inherit the older aggregate clock-window overlap with IO_BANK0.

The explicit `rp2350b` SIO and IO_BANK0 profiles expose GPIO0..47. GPIO30/31
occupy the upper two bits of the low SIO word; GPIO32..47 occupy bits0..15
of each `GPIO_HI_*` word. Direct, SET, CLR and XOR writes preserve the other
word. The chip pin map and GPIO attachment API translate a physical pad to
its register word and bit, so a sensor on GPIO47 does not drive GPIO15.
All six GPIO interrupt words and both PROC0 secure summary words cover the
bonded pins. The 30-pad profiles reject B-only pads and interrupt bits.

The ADC `rp2350b` profile has eight external inputs on GPIO40..47 and the
temperature sensor on input8. AINSEL is four bits and RROBIN is nine bits.
The existing five-input profiles keep temperature on input4. External
inputs stay at zero until an attached source drives them. Conversion
latency and paced ADC DMA remain outside the existing ADC model.

GPIO routes include the high-bank UART, SPI, I2C and PWM positions. PIO
GPIOBASE0 reaches GPIO0..31, including native motor pins30/31; changing
PIO GPIOBASE to16 for GPIO32..47 is not modeled. QSPI and USB pad bits in
SIO GPIO_HI, GPIO override behavior, physical analog accuracy and core1
remain outside this derivative's contract. SYSINFO.CHIP_ID retains the
existing unqualified value; no silicon revision parity is claimed.

ELF fast boot also compares both reset-vector words before deciding that
address0 aliases the application. A separate ROM can have the same initial
stack address as the application and a different reset handler. Such an
image needs VTOR at the application table, or SDK relocation copies ROM
instructions as interrupt vectors. This path does not execute a real
Raspberry Pi boot ROM or validate its flash boot sequence.

Source authority: [Raspberry Pi RP2350 variants](https://www.raspberrypi.com/products/rp2350/),
[RP2350 datasheet](https://datasheets.raspberrypi.com/rp2350/rp2350-datasheet.pdf),
and [pico-sdk hardware_regs at ee68c78d](https://github.com/raspberrypi/pico-sdk/tree/ee68c78d0afae2b69c03ae1a72bf5cc267a2d94c/src/rp2350/hardware_regs/include/hardware).
The register definitions used are `regs/sio.h`, `regs/io_bank0.h`,
`regs/adc.h`, `regs/sysinfo.h` and `platform_defs.h`. Behavior is covered by
`crates/core/tests/gpio_logic/rp2354b_gpio.rs`, the ADC unit tests and the
same-stack/different-vector loader regression. These checks establish the
specified contracts; they do not establish a complete flight-controller
runtime or a physical flight qualification.

## Clean-room ROM flash API and cacheless XIP

The three RP2350 chip descriptors share a functional ROM flash path. The
`RE` entry erases bytes to `0xff`; `RP` applies NOR bitwise AND, so programming
cannot change a zero bit back to one. The caller still executes the SDK's
range/alignment checks, cache maintenance, CS1 save/restore, ROM calls and
XIP-restore helper. The low-level hardware ROM APIs themselves do not check
arguments; the separate checked `flash_op` API remains unavailable.

The 64 MiB maintenance mirror at `0x18000000` recognizes operations 0..3
(invalidate/clean by set-way/address). The backing is coherent and has no
cache lines, so these operations complete immediately without changing flash
bytes. This includes the SDK's RP2350-E11 workaround at `0x1bffc001`.
Cache pinning and reserved operations return errors. The RP2040 SSI atomic
aliases at the same address are enabled only for the actual RP2040 SSI
endpoint; they cannot fold RP2350 maintenance addresses into another line.

QMI at `0x400d0000` retains the native memory-window configuration registers
and reset values used by the SDK's CS1 save/restore sequence. Direct serial
FIFO transfers and non-identity address translation return explicit errors.
This register contract does not simulate QSPI commands, serial timing,
flash busy timing, dirty cache writeback, or another core accessing XIP
while erase/program runs.

Silicon's boot ROM leaves a relocatable XIP-restore function in BOOTRAM.
For the exact bundled clean-room image, bus construction installs its
cacheless equivalent (`bx lr`) at `0x400e0000` and the documented no-OTP
FLASH_DEVINFO default at `0x400e0100`. The SDK copies and calls this helper
normally. FLASH_DEVINFO remains writable through the ROM data pointer.
A caller-supplied replacement ROM receives no synthetic BOOTRAM contents.
This is an explicit post-ROM fast-boot contract, not execution of the
manufacturer's flash boot sequence or evidence of TrustZone behavior.

[pinned cache driver](https://github.com/raspberrypi/pico-sdk/blob/ee68c78d0afae2b69c03ae1a72bf5cc267a2d94c/src/rp2_common/hardware_xip_cache/xip_cache.c),
and [QMI register definitions](https://github.com/raspberrypi/pico-sdk/blob/ee68c78d0afae2b69c03ae1a72bf5cc267a2d94c/src/rp2350/hardware_regs/include/hardware/regs/qmi.h).
The executable regression contracts are `rp2350_bootrom_lookup` and

No physical flash endurance, timing or board qualification is claimed.

## Explicitly not modeled

TrustZone / security partitions, second M33 core and SIO FIFO dual-core
bring-up, Hazard3 RISC-V cores, the real bootrom boot path (IMAGE_DEF scan,
XIP setup) and every ROM API not listed above (checked flash_op, OTP,
partition tables), the redundancy coprocessor (p7), TIMER1, HSTX/DVI, PIO v2-only instructions, OTP, SHA-256,
TRNG, direct QMI serial programming and non-identity translation. Sim86 claims several of these; we declare nothing
we do not model.
