# Microchip (Atmel) AT91RM9200 imported profile

## Measured profile

LabWired's onboarding profile for the imported Renode `at91rm9200` target is
narrowed to what the engine executes and the smoke exercises:

- **CPU:** the native ARM926EJ-S model (ARMv5TEJ, MIDR `0x41069265`). The
  silicon is an ARM920T (ARMv4T). Neither the pinned tlib nor the embedded
  engine has an ARM920T model; Renode's own platform
  (`platforms/cpus/at91rm9200.repl`) runs this part as tlib `arm926ej-s` with
  `ModelID 0x41009200`. LabWired uses the same CPU model but does **not**
  override MIDR, so ID-register reads return the ARM926EJ-S value. ARMv5TE
  instructions that an ARM920T would treat as undefined (for example `BLX`,
  `CLZ`, `LDRD`) execute instead of trapping. ARM926 Thumb execution is
  refused by the adapter.
- **Memory:** Renode's 0x30000-byte internal memory at `0x00000000`. The
  original import placed it at `0x08000000` (an STM32 default) and put
  192 KiB RAM at `0x20000000`; both were wrong and are corrected/removed. The
  256 MiB SDRAM at `0x20000000` (aliased at `0xC0000000`) is omitted.
- **Debug Unit (DBGU)** at `0xFFFFF200` on the SAM USART register map:
  `DBGU_SR` at 0x14 with TXRDY (bit 1) and TXEMPTY (bit 9) set when idle, RHR
  at 0x18, THR at 0x1C. TX is captured whether or not `DBGU_CR.TXEN` was
  written. Baud rate, `DBGU_CIDR`/`EXID`, interrupts and RX are not modelled.

Not modelled and omitted from the descriptor: the AIC, the system timer, the
PMC (Renode's PLLAR/PLLBR/MCKR constant-read scripts), PIO, USARTs, EMAC, USB,
MCI, SPI, TWI, SSC, the external bus interface and the MMU/caches as an
ARM920T implements them.

The earlier report on this page described a 2026-10-18 run of a Thumb
Cortex-M fixture (`uart-ok-thumbv7m.elf`) against the unnarrowed import. That
run never executed ARM9 code and is withdrawn.

## Smoke evidence

The committed A32 fixture `tests/fixtures/at91rm9200-dbgu-smoke.elf` is
assembled for `-mcpu=arm920t` (ARMv4T only), linked at `0x00000000` and
injected directly into the internal-memory window. It writes `DBGU_CR` RSTTX
then TXEN, polls `DBGU_SR.TXRDY` before each byte and writes
`AT91RM9200 DBGU SMOKE` to `DBGU_THR`, and then spins. It ran **100,000
ARM926EJ-S instructions** and passed the UART banner and bounded `max_steps`
assertions (JUnit: 3 cases, 0 failures); the final state has PC at the spin
loop (`0x38`) and the last `DBGU_SR` read `0x202` (TXRDY | TXEMPTY). With the
DBGU removed from the descriptor, the same fixture stops with a memory
violation at `0xFFFFF200` (`DBGU_CR`) and passes 0/2 checks (see
`docs/coverage/renode-onboarding/attempt-history/at91rm9200/2026-11-08-dbgu-negative-control/`).
The fixture does not boot through the boot ROM or exercise the MMU, caches,
interrupts, Thumb code or any ARMv5-only instruction.

The exact system manifest is `configs/systems/onboarding/at91rm9200.yaml`, the
smoke script is `examples/renode-onboarding/at91rm9200-dbgu-smoke.yaml`, and
the build recipe is
[`scripts/build_at91rm9200_dbgu_smoke.sh`](../../scripts/build_at91rm9200_dbgu_smoke.sh).
Per-target metrics, JUnit, UART output, simulator result, snapshot and logs are
under `docs/coverage/renode-onboarding/metrics/at91rm9200/`.

This is local CLI simulation evidence for the smoke assertions, not whole-SoC
coverage, ARM920T equivalence, Renode equivalence, or hardware confirmation.
