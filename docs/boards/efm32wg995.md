# EFM32WG995 Renode onboarding smoke

**Imported architecture:** ARM Cortex-M4F. The smoke binary uses the Cortex-M4
instruction subset and does not exercise the FPU.

## Bounded execution profile

`configs/chips/onboarding/efm32wg995.yaml` keeps the imported 256 KiB flash and
32 KiB RAM map and exposes only the model-backed UART0 register window at
`0x4000e000`. Other imported peripheral declarations were removed from this
execution profile because this round did not model or exercise them.

## Smoke evidence

The exact imported-system smoke in
`examples/renode-onboarding/efm32wg995-smoke.yaml` runs 100,000 instructions.
It asserts the `EFM32WG995 UART0 smoke` output and the configured `max_steps`
stop reason. Build and simulator logs, UART output, JUnit assertions, result
JSON, and a snapshot are recorded under
[`docs/coverage/renode-onboarding/metrics/efm32wg995/`](../coverage/renode-onboarding/metrics/efm32wg995/).
The initial attempt used the neighboring USART0 address, faulted on unmapped
MMIO, and is preserved under
[`docs/coverage/renode-onboarding/attempt-history/efm32wg995/`](../coverage/renode-onboarding/attempt-history/efm32wg995/).
The full imported inventory is summarized in the
[`Renode onboarding scoreboard`](../coverage/renode-onboarding-scoreboard.md).

This is repository CLI smoke evidence for the Cortex-M4 execution subset,
imported memory map, and UART0 path. It does not establish FPU behavior, full
EFM32WG995 peripheral coverage, hosted `labwired_verify` model verification,
or hardware confirmation.
