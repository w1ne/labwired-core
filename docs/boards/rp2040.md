## Support matrix

| Block | Status | Notes |
|-------|--------|-------|
| Cortex-M0+ core 0 | ✅ | Instruction path |
| Core 1 (second M0+) | ❌ / ⚠️ | Not a complete dual-core product story yet |
| UART0 | ✅ | Modelled (check register profile notes in chip yaml) |
| PIO0 | ⚠️ | Yaml-listed; full SM execution depth limited |
| I²C0 + BME280 | ✅ exercised in simulator | The Pico BME280 smoke reads the model's chip ID and raw temperature; direct model attachment does not test electrical pad routing |
| GPIO / SIO | ✅ exercised in simulator | The non-wireless Pico's GP25 LED follows the RP2040 SIO model; Pico W's LED is behind CYW43439 and is not covered |
| DMA / USB / ADC / SPI / PWM | ⚠️ | See the firmware-exercise matrix and per-block notes; coverage depth differs |
| External QSPI XIP | ⚠️ | Flash load path depends on image |

Firmware that touches unmodeled MMIO will hit `MemoryAccessViolation` or poll forever — that is intentional honesty.

## What it catches vs bench

**Strong:** Single-core logic demos that stay on modelled peripherals; agent/CLI oracle loops when assertions match reality.  
**Bench / later:** Full PIO programs, dual-core + SIO FIFOs, USB device stack, timing-sensitive bit-banging on incomplete GPIO.

## Pico + BME280 smoke

[`examples/rp2040-pico-bme280/`](../../examples/rp2040-pico-bme280/README.md)
connects an Adafruit BME280 model to I2C0 at `0x77`, records GP4/GP5 as SDA/SCL,
reads `CHIP_ID=0x60` and raw temperature `0x082DC0`, then observes four GP25
LED edges. The run logs are committed under
[`examples/rp2040-pico-bme280/evidence/`](../../examples/rp2040-pico-bme280/evidence/).
It is a local simulator smoke, not physical-board confirmation; the sensor model
is attached at the controller and electrical pull-ups and pad routing are not
verified.

## Pico W + BME280 profile

[`examples/rp2040-picow-bme280/`](../../examples/rp2040-picow-bme280/README.md)
adds the RP2040-based Pico W board variant with an external BME280 on I2C0
GP4/GP5 and UART0 diagnostic output. Its descriptor deliberately does not
claim the CYW43439 Wi-Fi/Bluetooth radio or the onboard LED connected through
`WL_GPIO0`; USB is also outside this smoke. The BME280 is attached at the
modeled I2C controller, so the test does not validate electrical pad routing
or pull-ups. Evidence and the live vendor status record are kept with the
example. This is breadth work within RP2040's #5 measured demand rank (12%),
not a new chip model.

## How to run

### CLI
```bash
cargo run -p labwired-cli -- run \
  --firmware path/to/firmware.elf \
  --system configs/systems/pico.yaml
```

### Playground
Pico-class lab on [app.labwired.com](https://app.labwired.com).

### Agent
[MCP](../agent/mcp.md) → describe board → run → **verify**. Do not claim PIO/USB success if the matrix says otherwise.
